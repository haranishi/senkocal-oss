# 選考カレンダー（仮）ユーザーストーリーとUX5階層

実装前に戦略層から書き、設計判断を導いた文書（2026-09-07・Fable）。要件は `01_requirements.md`、技術は `03_architecture.md`。

## ユーザーストーリー
本命ユーザー＝就活中の本人（第一顧客）。救う相手＝30 社ぶんの選考メールを見て、手でカレンダーに書き写している就活生。

| # | ユーザー | 欲しいことと理由 | 受け入れ条件 | 導いた設計判断 |
|---|---|---|---|---|
| US-1 | 応募者 | メールを開いてカレンダーに転記する往復をなくしたい。30 社ぶん繰り返すと必ず抜ける | 朝に確認画面を開くと、届いたメールが候補として並んでいる。1 件 2 タップで入る | 取り込みは時間トリガーで自動、登録だけ人が押す。「自動で入る」ではなく「候補が出て押すだけ」 |
| US-2 | 応募者 | 誤って登録された面接に行かない・行けない事故を避けたい | 候補には出典（件名・Gmail リンク）と確度が付き、日時を直してから登録できる | 完全自動を捨てる。編集をカードの中で完結させる。確度は文言で示す |
| US-3 | 応募者 | ES 締切と Web テスト締切を落としたくない。締切は「予定」ではなく「期限」 | 締切は終日予定で入り、前日 9:00 に通知が来る | 締切は時刻付き予定にしない（終日＋通知 900 分前）。タイトルに時刻を書く |
| US-4 | 応募者 | 「第1〜第3希望を選んでください」のメールを放置して選考が飛ぶのを防ぎたい | 日程調整メールは「要返信」として返信期限の日に入る。候補日が一覧に見える | 未確定の日時は予定にせず `schedule_request` として別扱い。候補日を並べて表示 |
| US-5 | 応募者 | メルマガやスカウト DM に埋もれて本物の案内を見落としたくない。かといって拾いすぎも困る | ノイズは折りたたみに残り、見逃しを後から確認できる。無視は 1 タップ | ノイズを消さず状態「ノイズ」で台帳に残す。一覧の既定は畳む |
| US-6 | 応募者 | 自分のメールを外のサービスに渡したくない | 動くのは自分の Google アカウントの中だけ。外部 API も LLM も使わない | GAS で完結。ルールベース抽出。スコープ最小・明示 |
| US-7 | 応募者（運用者） | 導入で詰まりたくない。clasp や OAuth 設定を覚えたくない | `.gs` と HTML を貼って `setup()` を 1 回実行し、Web アプリを「自分のみ」で配信するだけ | 貼るだけのビルド。本人の既存 GAS 案件と同じ導入手順に揃える |
| US-8 | 応募者 | 抽出が外れたときに、直せる場所が分かる | 台帳（スプレッドシート）で全部見える。較正ツールで実メールの当たり外れを表にできる | 台帳を正本にし、Web アプリは台帳の見え方の一つにする。較正ツールを P0 に置く |

## UX5階層
### ① 戦略
- 目標: 本人の就活で「選考メールの転記」をなくす。毎朝 1 回、確認画面で候補を押すだけにする。
- 差別化の源泉: **国内に「メールから自動で候補を作る」就活管理ツールが無い**（調査 §1-4）。**確認を挟む設計**（海外勢と同じ判断）。**Google アカウントの中で完結**（プライバシーと導入の軽さ）。
- 成功指標: 候補 1 件を 2 タップ以内で登録。本人の実メールで較正後、企業名・種別 90%、日時・締切 85%（NFR-04）。導入は 30 分以内。
- 戦略層で決めた制約: 自分専用。媒体サイトを叩かない。自動登録しない。メールを書き換えない。LLM を使わない。

### ② 要件
載せる＝取り込み・分類・日時と締切の抽出・企業名・台帳・確認画面・登録と取り消し・冪等・設定とトリガー・貼るだけビルド・較正ツール。P1＝日次ダイジェスト・訂正の学習・変更の追随。対象外＝媒体サイト・完全自動・メール書き換え・ES 本文・公開。

### ③ 構造
- 面は 3 つ。**Gmail → 台帳（スプレッドシート）→ 確認画面（Web アプリ）→ カレンダー**。台帳が正本、確認画面は台帳の見え方、カレンダーは出力。
- 取り込みの状態機（1 通）: 未処理 → 解析 → 候補（0〜n 件）／ノイズ → 処理済み。
- 候補の状態機: 候補 → 登録済み（→ 取り消しで 候補）／無視。ノイズ → （本人が「候補にする」）候補。エラー → 再試行で 候補。
- 確認画面の状態機: `loading` → `empty` | `list` | `error`。`list` 内でカードごとに 編集中 → 登録中 → 登録済み。
- 分岐と復帰: 企業名が取れない → カードで入力してから登録／日時が取れない → 締切候補か日程調整として出す。無ければ低確度に置く／登録に失敗 → カードに理由とやり直し／設定シートが壊れている → `error` に「setup() を実行」の案内。

### ④ 骨格
- 確認画面（スマホ 390 を基準・768／1440 は同じ 1 カラムを中央 680px 幅に）。上から: ヘッダー（製品名・最終取り込み時刻・「いま取り込む」）／まとめ行「明記の N 件をまとめて登録」（塗り・N=0 なら非表示）／区分ごとの見出し（「予定 3」「締切 2」「日程調整 1」「要確認 2」「ノイズ 8（畳む）」「登録済み N」）／カード列／フッター（台帳を開く・設定）。**最大の要素はカードの日時**（例「3/5（木）14:00〜15:00」）。
- カード: 1 行目＝日時（等幅・大。締切は「3/8（日）締切」と書き、時刻は下の小さい行に）＋種別チップ（【面接】【説明会】【締切】【要返信】）＋確度チップ（高「日時・企業名が明記」／中「一部推定あり」／低「要確認」。右端固定にしない）、2 行目＝企業名（太字・取れていなければ「企業名を入力」の入力欄）、3 行目＝件名（灰・1 行省略）、4 行目＝場所（あれば）、操作行＝「登録」（**ティール枠＋ティール文字の強調白抜き・高さ 44**。塗りはまとめ登録の 1 つだけ＝採点表 2「まとめ登録が主・個別が従」）と二次操作「無視」「編集」「Gmail で開く」（**白抜きボタン・高さ 44 以上を実測で満たす・要素間 8px 以上**。文字リンクにしない＝採点 r1）。日時も締切も無い候補は「登録」を出さず主操作を「編集して日時を入れる」にする（情報不足の扱いは 1 ルール）。確度チップは枠線のみ＋記号（◎明記／◯一部推定／△要確認）で種別チップ（塗り薄グレー）と見分け、語彙は「明記／一部推定／要確認」の 1 系統（まとめ登録「明記の N 件をまとめて登録」・区分「要確認 N 件」）。編集を開くとタイトル・開始・終了・締切・場所の入力が出て「この内容で登録」に変わる。
- 登録済みカード: 上段に「✓ 登録済み」のラベル、下段に日時「3/5（木）14:00〜15:00」（日付と時刻は途中で折り返さない。終日は「終日」。確度チップは出さない）＋「カレンダーで開く」「取り消す」（取り消すは末尾・色を落とす）。単体の登録・取り消しの結果も上部の帯で返し、登録直後の帯に「元に戻す」。
- 変更・中止（`change`）のカード: 日時行の下に「変更・中止の連絡です。予定の作成でなく、既に入れた予定の見直しに使ってください。」を 1 行出し、主操作は「Gmail で確認する」・「登録」は二次操作（変更後の新日時を入れる場合のため残す）。
- 必須が欠けたカード: 企業名なしの「登録」は `aria-disabled`＋灰色の見た目（押すと企業名欄へフォーカスして理由を出す）。日時なしは主操作を「編集して日時を入れる」にする＝情報不足の扱いは 1 ルール。登録済みは各区分に混ぜず、**最下部の区分「登録済み N 件」**に置く（390 の初期表示に操作対象が入るように）。まとめ登録の対象は **1 つの規則**＝「確度: 高（明記）・企業名あり・開始日時または締切あり・種別が日程調整と変更でない・過去日でない」を満たす候補（締切候補も含む＝終日予定なので安全側。日程調整は返信が要るので除く。注記にはこの条件を平易に書き、対象の企業名を列挙する）。`error` は見出し「初期設定がまだです」＋本文 1 文の 2 段（`empty` と階層をそろえる）。注記に対象を近い日から列挙し、押下後は帯「N 件を登録しました／まとめて取り消す」を出す。区分は 6 つ＝予定・締切・日程調整・要確認・ノイズ（畳む）・登録済み（開いた `<details>`・最下部）。
- 日程調整カード: 候補日をチップで並べ、「返信期限 3/8」＋「【要返信】として登録」。
- ノイズ: `<details>` で畳む（▸／▾・高さ 44 の淡い面・閉じているときは中身を描かない・summary に「5 件は候補から外しています」）。開くと件名と送信者だけの薄い行＋「候補にする」。
- `empty`: 「候補はありません。次の取り込みは 2 時間ごと」＋「いま取り込む」。`error`: 「初期設定がまだです。Apps Script のエディタで setup を一度実行してから、下のボタンを押してください。」＋「もう一度読み込む」。error の間はヘッダーの「いま取り込む」を非表示（`empty` と同じ）。ヘッダー 2 行目は「最終取り込み hh:mm・メール N 件から候補 M 件」で `empty` も同形。フッター（台帳を開く・設定）は 3 状態で同じ。`list` の注記に「Gmail から拾った候補です。押すまでカレンダーには入りません。」
- 台帳（シート）は見出し固定・状態列にデータの入力規則（候補／登録済み／無視／ノイズ／エラー＋**登録**＝手動登録の合図。`registerMarked()` が拾う）。列順は `docs/03` §3。

### ⑤ 表層
- 無彩色＋アクセント 1 色（ティール `#0f766e`・白文字とのコントラスト 5.9:1）。ダーク: 背景 `#0f1217`／面 `#171b22`／文字 `#e8ebf0`／アクセント `#5eead4`（ボタン文字は `#0f1217`）。赤緑に意味を持たせない。
- 日時は `ui-monospace, "SF Mono", Menlo, monospace`＋`tabular-nums`。本文は `system-ui, -apple-system, "Hiragino Sans", "Noto Sans JP", sans-serif`。
- 角丸 10px・影 1 種類・カード間 12px。モーションは登録完了のフェードだけ（`prefers-reduced-motion` で無効）。日本語 UI。
- HtmlService の IFRAME サンドボックスで動くので、外部リンクは `target="_blank"`、`<base target="_top">` は使わない。外部フォント・CDN は使わない（インライン CSS/JS の単一ファイル）。

## この5階層を通して変わった実装（8件）
1. 「メールが来たら自動でカレンダーに入る」を捨て、「候補を作って人が押す」にした（誤登録の非対称なコスト。海外勢と同じ判断）
2. 締切を時刻付き予定ではなく「終日＋前日 9:00 の通知」にした（期限は時間枠ではない）
3. 日程調整メールを予定にせず「要返信」の別種別にした（未確定の日時をカレンダーに入れない）
4. ノイズを捨てず台帳に残し、画面では畳んだ（見逃しの確認ができる）
5. 確認画面を Web アプリにしつつ、台帳（シート）を正本にした（Web アプリを配信しなくても運用できる）
6. LLM 解析を初版から外し、ルールベース＋較正ツールにした（本文を外に出さない。実メールで直す周回を前提にする）
7. 処理済みの記録をメールのラベルではなく台帳に持ち、スコープを `gmail.readonly` に限定した
8. 貼るだけの 3 ファイルにビルドし、clasp・OAuth クライアントを導入手順から外した
